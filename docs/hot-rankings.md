# Hot ranking contract

Status: canonical

Contract version: registry schema 2

## Metric

`Hot` ranks catalog entries by the absolute net change in GitHub's public
`stargazers_count` between two successful registry observations:

```text
net_star_growth = current_star_count - baseline_star_count
```

This is not gross new-star activity: unstars can make the value smaller or
negative. It is not based on Cliff usage, views, installs, accounts, or other
user telemetry.

## Windows

The published window IDs are `7d` and `30d`. For each window, the builder:

1. Starts from the current successful observation set.
2. Selects the oldest snapshot at or after the requested cutoff that has at
   least one repository in common with the current observation set, never a
   snapshot that would silently measure a longer period.
3. Joins repositories by stable GitHub numeric repository ID.
4. Emits a delta only when that repository has successful observations at
   both endpoints.

A window is `complete` when its baseline falls on the requested UTC cutoff
date. During initial collection, a newer baseline is valid but partial; the
wire metadata exposes the exact `from` and `to` timestamps. A window with no
usable second snapshot is unavailable and has no endpoint timestamps.

## Wire shape

`index.json` schema 2 adds:

- `star_windows["7d"|"30d"]`: `requested_days`, optional `from`/`to`, and
  `complete`.
- `apps[].star_growth["7d"|"30d"]`: the signed integer delta.

Map membership is significant. A present `0` is a measured zero change. A
missing key means coverage was unavailable and must not be rendered as zero.
Schema 1 clients remain compatible because both additions are optional.

The Cliff client sorts a Hot window by delta descending, then lifetime stars
descending, then app name ascending.

## Snapshot invariants

- Snapshots are date-stamped JSON files under `data/stars/`.
- Repository observations are ordered by stable GitHub ID for deterministic
  output and retain the current `owner/name` for auditability.
- GitHub response ETags are retained and sent on the next collection run.
  A `304 Not Modified` is a successful current observation; this keeps daily
  collection within the Actions token's API budget as the catalog grows.
- Failed GitHub requests are omitted, never recorded as zero.
- The regular index may reuse the latest successful lifetime count after a
  request failure, but it must not publish a growth delta without a current
  observation.
- Snapshot files are generated by CI and retained in Git so index generation
  remains reproducible and ranking history is not hidden in an external
  service.
